# k8s/secrets — Sealed Secret templates

## Overview

This directory contains **template** SealedSecret manifests.  The `*.template.yaml`
files contain **placeholder** ciphertext — they are for documentation purposes only
and must **not** be applied directly to a cluster.

The actual sealed files (generated by `kubeseal`) should be placed here as
`*.yaml` (without `.template`) after sealing against your cluster's public key.
Those files are safe to commit because only the cluster that holds the matching
private key can decrypt them.

## Files

| File | Secret name | Type | Namespaces |
|------|-------------|------|------------|
| `my-app-secrets.template.yaml` | `my-app-secrets` | `Opaque` | `production`, `staging` |
| `docker-registry-secret.template.yaml` | `docker-registry-secret` | `kubernetes.io/dockerconfigjson` | `production`, `staging` |

## How to seal a secret

Use `scripts/seal-secret.sh` for generic (`Opaque`) secrets:

```bash
scripts/seal-secret.sh production my-app-secrets \
    db-host=mydb.internal \
    db-password=supersecret \
  > k8s/secrets/my-app-secrets.yaml
```

For `docker-registry` typed secrets use `kubectl create secret docker-registry`
piped through `kubeseal` directly (see header comment in the template file).

## Important notes

1. **Ciphertext is per-cluster.** A secret sealed against cluster A cannot be
   decrypted by cluster B. You must re-seal when moving to a new cluster.
2. **Never commit plaintext** — only commit the `kubeseal` output.
3. **Back up the controller key.** If the sealed-secrets controller key is lost,
   all sealed secrets become unrecoverable. See `docs/secrets.md` for the backup
   procedure.
4. **Rotation.** To rotate a secret: re-seal the new value → commit → Argo CD
   syncs the SealedSecret → the controller decrypts and updates the plain Secret
   in-cluster.
